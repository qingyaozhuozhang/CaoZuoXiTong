# 适用范围与限制

本文用于界定可展示、可验收的能力，防止将测试覆盖扩大为未验证的兼容性承诺。具体实现见[架构与实现](architecture.md)，接口契约见 [API 使用说明](api.md)，量化验收见[测试与性能评测](testing.md)。

## 1. 平台与部署

| 项目 | 当前范围 |
| --- | --- |
| 操作系统/架构 | Linux x86_64 与 ARM64 后端；提交 `b3988f8` 的原生双架构 full / UBSan 均通过，见[固定验证材料](archive/README.md) |
| 调用约定 | x86_64：System V AMD64 ABI；ARM64：常规 AAPCS64 |
| 构建环境 | GCC、GNU make、glibc；评测脚本需要 Python 3.9+ |
| 目标访问 | 需要允许 ptrace、读取 `/proc/<pid>/maps` 并访问目标内存 |
| 注入内存 | 代码池与返回 stub 使用 RWX 映射；严格 W^X/执行内存策略可能拒绝 |
| 控制并发 | 同一上下文仅一个 tracer 控制线程和一个事件消费者 |

每份构建只跟踪相同架构的目标，不支持 x86_64 控制器直接控制 ARM64 进程。Windows、macOS、32 位模式与任意语言运行时的特殊调用约定不属于当前范围。ASLR/PIE 支持已加载 ELF 的地址解析和可达代码区分配；四个作业均通过 8 次独立 exec 的主程序及共享库地址变化、参数/返回和入口恢复检查，仍需要入口指令、地址距离、映射权限等条件同时满足。

本页当前结论对应 GitHub Actions 运行 `45958959682`、提交 `b3988f82b2108ce99bdd192855b367483477bde8`。单架构需求表中的 A1 SKIP 表示需联合另一架构报告；两架构同提交结果已满足该条件。UBSan 的性能、内核对照及真实合流三项 SKIP 属于正确性作业分工，两架构 full 已完成相应实测。修改实现后的结论需要重新建立验证证据。

控制进程设置了 `PTRACE_O_EXITKILL`。tracer 异常退出时，被跟踪的目标可能被内核终止。当前没有提供 tracer 崩溃后自动恢复原指令、自动续跑目标或故障接管机制；演示应使用其自行启动的测试进程，并正常清理退出。

## 2. 指令、符号与代码生命周期

x86_64 入口补丁至少需要 5 字节的完整、可重定位指令。有限解码器拒绝 VEX/EVEX、地址宽度覆盖、部分特殊指令和过短入口；支持保存 AVX 状态不等于支持改写所有 AVX 指令。

ARM64 使用 4 字节直接 B，要求补丁及续接均可达。入口 BTI 被保留，实际补丁可位于符号地址加 4；普通 RET 可搬迁。ADR/ADRP 展开，B/条件分支/CBZ/TBZ/literal load 执行范围检查。BL、SVC、PAC 等不支持的入口编码被拒绝。部分函数的控制流、PAC 返回或间接着陆约束不能由单条入口检查完全推断，调用方须确保目标符合常规受支持调用约定。

符号查找不负责调用 GNU IFUNC 解析器取得最终实现，也不自动提供类型、结构体、DWARF 或源码级参数信息。地址接口要求调用方提供目标进程真实地址。不能仅因符号同名，就使用 tracer 自身的地址。

运行期间目标 `exec` 时，`ludp_poll` 或 `ludp_quiesce` 返回 `ESTALE`。调用 `ludp_detach` 释放新镜像的跟踪停止，随后可对同一 PID 重新附加并按新地址安装探针。旧会话的映射和探针不会迁移。

目标在安全点通过 `dlclose` 实际卸载动态库后，可以移除旧探针。工具核对入口映射和补丁，避免把旧指令写入已复用的地址。旧探针启用、禁用或热更新返回 `ESTALE`，移除后可对重新加载的库安装新探针。应用需先等待涉及该库的调用返回，并在卸载 A4 回调所在的库之前清除回调。JIT、自修改代码和 fork 后子进程的探针迁移仍属于当前限制。

## 3. 安全点、多线程与信号

F7 的范围是已验证的多线程事件生产、线程附加/创建/退出维护、信号转发和受控阶段的代码修改。它不保证目标在任意指令位置暂停后都可立即热插拔。

全线程暂停可能发生在入口被覆盖区域中间，也可能留下指向旧 trampoline 的在途执行。应用需先阻止新增调用、等待在途调用完成并建立安全点，再执行安装、启停、链重建、更新和清理。`ludp_quiesce()` 不会自动完成这些应用条件。

清理与更新会检查部分活跃状态并返回 `EBUSY`，但不能用这些检查替代安全点协议。失败恢复也可能失败；`EIO` 后目标可能保持暂停，调用方必须保留上下文处理错误，不能直接声称热更新已回滚并恢复运行。

测试覆盖普通信号重入和 64 次 signal-delivery stop 与暂停竞争，不构成对所有信号、job-control、异步异常或任意信号处理器的全面保证。tracer 必须持续处理 `ludp_poll()`；A4 回调在信号重入环境下还须满足自身的可重入与信号上下文约束。

## 4. 参数与返回模式

`args[0..5]` 仅采集六个整数类参数寄存器：x86_64 的 RDI/RSI/RDX/RCX/R8/R9 或 ARM64 的 X0–X5。ARM64 X6/X7 和栈参数保持透传，不自动导出。浮点形参、混合参数、可变参数、栈上传递的值、结构体和隐藏参数需按 ABI 单独解释，当前不提供通用自动解码。

返回事件提供 RAX/RDX/XMM0（x86_64）或 X0/X1/V0（ARM64）原始值，浮点字段统一使用 `fp_ret`，不覆盖任意聚合返回、完整多向量返回或 x87 返回值提取。寄存器状态保护与“将所有返回寄存器导出为事件”是不同能力。

返回模式依赖被探测调用正常执行 ABI 返回。不支持跨被探测栈帧的 `longjmp`、C++ 异常展开、线程取消、协程换栈、`noreturn`、CET shadow stack 或 ARM64 GCS/PAC 返回协议。异常离开可能留下占用记录或改写后的返回地址；4096 个在途记录耗尽时只记录丢失并让原函数继续。

同地址探针链只支持入口模式。不能在同一地址叠加返回探针，也不能在存在同地址链时任意切换为返回模式。

## 5. A4 回调的透明性边界

回调在目标线程中同步运行，额外执行时间属于目标的实际延迟。它不是后台任务，不能等待 tracer、长期阻塞或递归进入同一被探测入口。

x86_64 的 XSAVE 路径覆盖启用的 x87/SSE/AVX/AVX-512 浮点与向量状态，旧平台回退 FXSAVE；AMX tile 状态未保存。本次 full / UBSan 均通过 AVX 寄存器专项检查，但未提供 AVX-512 专项哨兵测试；不能从保存路径存在推导全部扩展状态已实测。回调须遵守 ABI，且不能修改未保护的扩展状态。

ARM64 保存固定宽度 Q0–Q31、FPCR/FPSR 及通用寄存器/NZCV，本次 full / UBSan 均通过 SIMD 专项检查；未实现 SVE/SME 扩展状态保存。附加检查拒绝活动 SVE/SME 上下文和启用的 GCS，但不能防止目标在恢复后启用扩展；整个会话须持续满足该约束。仅具备 SVE 硬件能力且未激活相关上下文的普通程序不因此被排除。

寄存器恢复不会撤销回调对目标内存、TLS、`errno`、锁、文件或其他应用状态的修改。目标原本持有的锁可能使回调调用普通库函数发生重入或死锁。回调应保持短小、可重入、非阻塞；上下文指针仅在该次调用期间有效。

## 6. A3 事件合流的完成边界

已实现 TSC/CNTVCT 原始采样、tracer 侧 CLOCK_MONOTONIC 校准换算、可用时的 Linux TID 映射，以及 perf-script 风格文本。`event_stream_demo` 和真实 ftrace 合流流程在独立 tracefs instance 中使用 `mono` 时钟采集内核 getpid 事件，与用户态入口/返回事件合并分析。合流脚本、离线格式验证和真实采集分别判定。

提交 `b3988f8` 的两架构均通过真实采集：各 100 次调用、200 条用户态事件和 100 条内核事件，计数、TID、CPU、配对、时间单调性及无丢失检查通过。内核事件超出对应入口/返回区间的最大距离为 x86_64 1623 ns、ARM64 6091 ns，低于预设 100,000 ns 容差。该结果建立了固定单 CPU、约 0.1 秒会话的合流证据，不能推广为任意会话的时钟误差上界；具体结果见[测试与量化验收规范](testing.md)。

具体限制包括：

- `monotonic_ns` 是事件硬件计数的换算估计，由消费侧补充；不是热路径直接读取的 CLOCK_MONOTONIC，也不是消费发生时的当前时间。
- 校准只在 attach 时进行，没有公开的周期重校准接口或误差上界。x86_64 的非恒定 TSC、跨 CPU 偏移，以及两种架构的长会话和虚拟化环境均需另行验证。ARM64 使用 CNTFRQ 固定频率，不以 CPU 主频推算计数频率。
- 入口计数在过滤和可选 A4 回调之后记录，不能代表原始函数入口的精确时刻或回调起始时刻。
- CPU 编号由调用方填写，负值显示为 0；未采集真实 CPU。TID 无法映射时为 0，文本会回退到 pid，这种回退不能当作真实线程标识。
- 环按领取序号消费，不保证多线程事件时间戳严格排序；跨流分析仍需排序和时钟一致性验证。
- 默认文本只展示部分字段，完整六参数和浮点返回信息保留在结构化事件中。
- 当前原生证据来自 ftrace `syscalls:sys_enter_getpid`；合流输出为 perf-script 风格文本，不是 `perf.data`，未验证所有 perf/kprobe 采集器。

## 7. 容量、资源与性能结论

默认环为 4,194,304 条，约 544 MiB 虚拟映射，物理页按需触达；并非低于该值的固定物理内存占用。事件环满时丢弃新事件，返回槽满时放弃该次返回采集，必须同时检查 `overflow` 和 `return_missed`。低丢失率或短时演示成功不能代替长时、峰值负载下的资源评测。

“无探针触发时零开销”应具体解释：未安装探针，或某地址所有探针关闭并恢复入口后，没有该探针的目标入口执行路径；attach 仍有线程跟踪、映射与控制资源成本。过滤拒绝依然执行跳转、现场保存和过滤；同地址仍有其他启用探针时也仍有执行成本。基准 `inert - baseline` 的微小差值不能证明整个会话没有任何系统成本。

当前标准性能报告主要度量百万次 `getpid` 的无探针、仅附加、入口、入口+返回和可用时的内核 uprobe。它不自动证明带任意 A4 回调、长同地址链、16 探针并发、长时运行、所有 CPU 或溢出场景均满足 `< 1000 ns`。

插入 `< 10 ms` 从已经附加且到达安全点之后开始。完整清理 `cleanup_ms` 从移除开始，经过入口恢复校验，直到 `ludp_detach` 完成映射释放和会话分离，并纳入 `< 10 ms` 门禁；另保留各分段耗时。本次最大完整清理分别为 x86_64 2.464 ms、ARM64 1.653 ms，两架构均达标。等待应用安全点和 attach 不属于这段清理时间。x86_64 attach 自带约 5 ms 时间校准等待；ARM64 根据 CNTFRQ 和单调时钟锚点换算，不包含该等待，不能将探针安装结果直接当作完整会话延迟。

普通本地模式下，内核 uprobe 或 ftrace 可能因权限或设备不可用显示 `SKIP`。CI full 同时要求实际 uprobe 对照与 A3 合流；缺失任一项即失败，并保留原因。本次两架构均取得 5/5 轮内核 uprobe 样本，实测结果见[测试与量化验收规范](testing.md)；赛题的 `1500–3000 ns` 仅为参考范围。内核采样字段、缓冲与用户态全事件采集方式不同，不构成相同输出工作量的严格性能对比。性能报告须绑定提交、机器、环境、轮次、原始日志与测量方法。

为降低大环首次触页和回收成本，未启用 seccomp 且可确认策略的暂停线程允许请求可选大页建议；内核不保证实际分配。四会话生命周期回归包含“madvise 会终止目标”的 seccomp 场景，已经验证建议跳过后仍可正常插入、采集、清理和退出；这不表示任意 seccomp 策略都允许必需的注入系统调用。

## 8. 后续验收方向

| 方向 | 需要补充的工程与证据 |
| --- | --- |
| 后续版本回归 | 实现或验证流程变化后，重新取得同提交的双架构 full / UBSan 结果 |
| A3 扩展验证 | 单 CPU 短会话真实合流之外的跨 CPU、长会话时钟误差验证 |
| 指定验收机复测 | 按相同配置复现已通过的内核对照、完整清理与真实合流，记录该机器上的原始样本 |
| 更广运行时兼容 | 对异常展开、派生进程迁移、JIT 和 CET 等逐项设计与专项回归 |
| 扩展性能评测 | 过滤通过/拒绝、A4、并发链、多线程和不同容量下的开销与丢失率 |

以上为后续维护或扩展方向，不代表当前原生验证缺失。已有结果不自动适用于修改后的实现，交叉编译和模拟器也不能代替原生 ARM64 runner 的功能与性能结果。正式展示应使用[演示指南](demo.md)与[测试说明](testing.md)中可复现的范围。
