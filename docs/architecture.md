# 架构与实现

LUDP（Lightweight Dynamic Probe for User Space）提供 Linux x86_64 和 ARM64 两套用户态动态探针后端，分别遵循 System V AMD64 ABI 与 AAPCS64。控制进程使用 `ptrace` 协调目标线程并安装代码；探针触发后通过用户态跳转完成参数采集、可选回调和返回值记录。控制器和目标进程必须使用同一架构，构建时依据编译器目标选择后端。A1 的原生验收需同一提交在两种 GitHub Actions runner 上分别通过；`3ffd736` 已有[双架构归档](archive/README.md)，当前改进需以新一轮 CI 复验。

本文描述当前源码的设计与行为。运行条件和未覆盖场景见[适用范围与限制](limitations.md)，接口见[API 使用说明](api.md)，复现实验见[测试与性能评测](testing.md)，演示流程见[演示指南](demo.md)。

控制路径与命中路径分工如下：

```mermaid
flowchart LR
    A[控制进程：单个控制线程] --> B[ptrace 暂停与恢复]
    A --> C[解析 ELF 与重定位入口指令]
    C --> D[目标函数入口：JMP 或 B]
    D --> E[用户态 trampoline]
    E --> F[原函数]
    F --> G[可选 return stub]
    E --> H[目标进程事件环]
    G --> H
    H --> I[控制进程：单消费者]
    I --> J[结构化事件与 perf-script 风格文本]
```

库自身的事件热路径不使用 `int3`、`ptrace` 或系统调用。目标函数原有的系统调用，以及用户提供的 A4 回调行为，不属于这一保证。安装、线程维护、跨进程读取和清理仍需要内核参与。

## 2. 入口探针与地址定位（F1）

安装时先保存原入口指令，在目标附近分配可达代码区，再写入用户态分支。trampoline 完成采集后执行重定位的原指令，并继续原函数。两套后端的补丁规则如下：

| 项目 | x86_64 | ARM64 |
| --- | --- | --- |
| 入口补丁 | 5 字节 `JMP rel32`，完整指令边界多余字节填 NOP | 4 字节 `B imm26`，地址须 4 字节对齐 |
| 分支可达范围 | 相对下一条指令约 ±2 GiB | 相对当前指令 -128 MiB 到 +128 MiB−4 字节 |
| 入口着陆指令 | 按解码边界处理 | 保留原入口 BTI，存在 BTI 时在 `入口 + 4` 安装补丁 |
| 重定位 | 受支持的 RIP 相对寻址及相对分支 | ADR/ADRP 展开为 MOVZ/MOVK；B、条件分支、CBZ/CBNZ、TBZ/TBNZ 和 literal load 重新编码 |
| 拒绝条件 | 过短入口、VEX/EVEX、部分特殊编码或位移越界 | BL、SVC、PAC 等不支持入口；分支或 literal 位移越界；不安全编码 |

ARM64 的普通 RET 可以完整搬迁，因此不能沿用 x86_64 的“单条 RET 太短”拒绝条件。BTI 的保留不代表支持所有 PAC/GCS 程序；扩展状态限制见[适用范围](limitations.md)。ADR/ADRP 展开不借用额外寄存器，续接采用直接分支，避免破坏目标入口的 X16/X17 等现场。

共享库附近的主代码池不可达时，库尝试在目标地址附近分配辅助代码区。分配、范围检查或重定位失败时拒绝安装。验证辅助函数使用可补丁入口，真实 `getpid` 由共享库基准和多线程用例覆盖。ARM64 写代码通过 `/proc/<pid>/mem` 的 `pwrite` 或 ptrace 后备路径，由内核 `copy_to_user_page()` 完成指令缓存同步；不使用 `process_vm_writev` 写 ARM64 代码。

符号解析读取 `/proc/<pid>/maps` 与 ELF，主程序通过 `/proc/<pid>/exe` 精确匹配，运行时地址考虑加载偏移。存在 section header 时读取符号表；缺失时尝试 `PT_DYNAMIC`、`DT_HASH`/`DT_GNU_HASH` 与虚拟地址到文件偏移的转换。GNU IFUNC 的 `st_value` 指向解析器，符号接口明确拒绝将其当作最终函数。调用方可在确认实际实现地址后使用地址接口。

[`aslr_pie_validation.c`](../Proj40/aslr_pie_validation.c) 通过 8 次独立 exec 分别验证主程序 PIE 与共享库符号，检查实际装载地址发生变化，并核验参数、返回值和入口恢复；该流程补充了 fork 继承同一布局的验证范围。

## 3. 参数、返回值与上下文（F2、F3）

### 3.1 参数表示

`args[0..5]` 在 x86_64 上记录 `RDI、RSI、RDX、RCX、R8、R9`，在 ARM64 上记录 `X0–X5` 的原始 64 位值。它们对应 ABI 的整数类寄存器参数，不是所有函数的前六个源代码形参。ARM64 的 X6/X7 和后续栈参数保持透传，但不写入当前六参数事件结构。浮点、混合参数、结构体以及隐藏返回指针必须按真实函数签名解释；库不自动解引用指针或读取栈参数。

### 3.2 返回探针

入口+返回模式从预分配的 4096 个记录中原子领取一个槽位，保存调用者返回地址和入口参数。x86_64 改写栈返回地址，ARM64 改写 X30/LR，均指向该槽位的唯一 return stub。函数正常返回后，stub 记录返回寄存器、释放记录并继续原调用者。x86_64 导出 RAX/RDX/XMM0，ARM64 导出 X0/X1/V0。

入口与返回通过非零 `call_id` 关联。`retval`、`retval_hi` 和 `fp_ret[16]` 是寄存器原始内容，支持按签名解释整数、双寄存器整数或首个向量返回寄存器中的浮点结果；旧字段 `xmm0` 与 `fp_ret` 共享布局，保留为兼容别名；它们不构成通用结构体返回值反序列化接口。

返回记录耗尽时，库不替换该次调用的返回地址，原函数仍正常执行，入口事件的 `call_id` 为 0，并增加 `ludp_return_missed()`。事件环溢出还可能单独丢失入口或返回事件，因此分析程序应检查两个丢失计数，不能只按事件是否配对判断目标调用是否执行。

### 3.3 状态保护

x86_64 普通路径保存被使用的通用寄存器和 RFLAGS，保留 128 字节 red zone；未使用的 callee-saved 寄存器不改写。ARM64 保存 X0–X30 和 NZCV，保持 SP 的 16 字节对齐；普通采集不修改 SIMD/浮点控制状态。返回路径复制 XMM0/V0 至事件。A4 调用会额外保存并恢复浮点和向量状态，详见第 7 节。

正常返回、递归、十参数透传、信号重入均有专项用例。x86_64 哨兵覆盖 GPR/RFLAGS/x87/SSE/red zone；ARM64 哨兵对比 X0–X30、SP、NZCV、FPCR/FPSR 和 Q0–Q31。这些测试不能扩展为对异常展开、任意汇编调用约定或所有处理器扩展状态的保证。

## 4. 注册表、启停与清理（F4–F6）

注册表最多容纳 256 个探针。每个探针拥有 ID、目标地址、原始指令、trampoline、配置、版本号和已消费入口计数。删除后的注册表槽位与符合条件的代码槽位可以复用。

不同地址独立安装补丁，共享一个事件环。同一地址仅允许入口探针叠加，执行顺序为较新探针到较旧探针；只有最后一个启用探针执行重定位的原指令。同地址链最多 256 项。任何一项带返回模式时，该地址不能再叠加其他探针。

`enable`/`disable` 重建启用链；全部关闭时恢复原入口字节。关闭仅影响后续入口，已经开始的返回探针仍需执行，队列中已有事件也不会清空。重复相同启停操作幂等。

移除会检查代码区中的线程、在途返回记录和回调活跃计数，不能回收时返回 `EBUSY`。移除最后一个探针后，返回槽和辅助代码区可回收；事件环和主代码池保留到会话分离。`ludp_detach()` 成功时恢复入口、释放会话登记的远程映射、分离线程并销毁上下文。失败时保留上下文供调用方继续处理，不能把失败当作已经清理。

## 5. 线程协调与信号处理（F7）

| 阶段 | 处理方式 |
| --- | --- |
| 初次附加 | 枚举 `/proc/<pid>/task`，逐线程 `PTRACE_SEIZE`，记录跟踪和停止状态 |
| 结构修改 | `quiesce()` 发送 `PTRACE_INTERRUPT`，收集停止事件后修改代码 |
| 动态创建线程 | `ludp_poll()` 处理 `PTRACE_EVENT_CLONE` 并维护新线程 |
| 线程退出 | 根据 wait 状态与 `/proc` 刷新删除对应 TID 和元数据 |
| 真实信号停止 | 暂存 signal-delivery stop，在恢复或分离时转发 |
| 远程系统调用 | 选择停在用户态的可用线程，避免破坏阻塞 syscall 的 restart 现场 |
| 控制异常 | `PTRACE_O_EXITKILL` 使 tracer 异常退出时内核终止被跟踪目标 |

远程系统调用使用 `PTRACE_O_TRACESYSGOOD` 区分 syscall-stop 与普通信号停止。若所有可选线程均处于不适宜注入的状态，操作可返回 `EBUSY`，不会把阻塞在 futex 的主线程强行作为可用执行现场。

等待停止事件时先短轮询，再逐步退避，避免每次远程系统调用都叠加固定 1 ms 睡眠。超时依据单调时钟截止时间计算，重试、信号打断和调度延迟计入总等待；优化不改变停止状态及信号交付检查。

同一 `ludp_ctx` 由一个 tracer 控制线程驱动，事件由一个消费者读取。控制线程应持续调用 `ludp_poll()`；只读取事件而不处理 ptrace 停止，可能让新线程或收到信号的线程停住。

**暂停线程不是应用安全点的充分条件。** 线程可能停在即将覆盖的入口指令中间，或仍有路径指向要修改的 trampoline。安装、链重建、启停、热更新和移除必须由应用协议协调到安全点：阻止新的目标调用，等待已有调用和回调退出，确保相关线程不在待改写代码区，再进行操作。演示和专项测试通过受控阶段实现这一协议。

## 6. 多生产者事件环

目标进程各线程直接写入同一个环形缓冲：CAS 领取逻辑序号，写入独占槽位，最后发布该槽的 ready 序号。消费者只读取连续已发布的前缀，并推进消费水位。序号、水位位于不同缓存行，ready 数组与事件数组分离，便于批量跨进程读取。

生产者不等待较早序号的生产者发布，避免某线程被抢占或信号重入时形成提交等待死锁。环满时丢弃新事件并增加 `overflow`，不覆盖尚未消费的数据。较早槽位未发布会暂时阻塞消费者推进；这是一种顺序消费约束，并不表示目标进程所有线程都会等待它。

远端事件为固定 128 字节，公共事件为 144 字节，后 16 字节由 tracer 补充。默认容量 `2^22 = 4,194,304` 条，映射约 544 MiB（事件 512 MiB、ready 数组 32 MiB，另加头部）；物理页按需触达。`LUDP_RING_CAP` 可配置为 16 到 `2^22` 之间的 2 的幂，详细用法见 [API 使用说明](api.md)。

对至少 2 MiB 的事件环，控制侧在所有暂停线程均确认未启用 seccomp 时请求 `MADV_HUGEPAGE`，以减少大规模采集的首次触页和页表回收成本；`LUDP_HUGEPAGES=0` 可关闭。启用 seccomp 或无法确认状态时直接跳过可选 syscall。该建议受内核策略与内存条件影响，拒绝或不可用时保留普通页和相同容量；远程调用事务本身失败仍作为错误处理。是否降低完整清理延迟由基准实测，不从建议成功推断。

## 7. 条件探针、回调与更新（A2、A4、A5）

### 7.1 条件过滤

A2 对六个整数类参数中的一个进行无符号比较，支持 NONE、EQ、NE、MASK_EQ、LT、LE、GT、GE。判断位于保存入口寄存器之后、回调与返回槽领取之前。过滤不通过时恢复现场并执行原函数，不调用回调、不写事件、不申请返回槽，但仍承担入口跳转与过滤的执行成本。

### 7.2 目标进程回调

A4 在目标线程内同步调用 `void callback(const ludp_call_context *)`。上下文包含探针 ID、六个原始参数与 `user_data`，只在本次回调期间有效。回调地址需要处于目标进程可执行映射中，安装与更新在暂停后再次检查地址。

x86_64 回调路径通过 CPUID/XCR0 选择 XSAVE/XRSTOR，保存已启用的 x87、SSE、AVX 和 AVX-512 状态，保存区按 64 字节对齐；不具备条件时回退 FXSAVE/FXRSTOR。AMX tile 未纳入保护范围。ARM64 路径保存 Q0–Q31 共 512 字节及 FPCR/FPSR，恢复后再执行原函数。回调必须遵循对应平台 ABI。ARM64 附加时拒绝活动 SVE/SME 上下文与启用的 GCS；会话期间动态启用这些扩展状态不受支持。

活跃回调计数保护清理和更新。回调必须短小、可重入且非阻塞，不得递归调用同一探针、异常展开、`longjmp`、保存上下文指针或依赖 tracer 同步；它运行在目标线程现有的锁和信号环境中。回调不能使用未保护的 AMX、SVE 或 SME 状态，卸载其代码前必须先清除回调并等待在途执行完成。

### 7.3 安全点更新

A5 接受完整的 `ludp_probe_config`，可更新过滤、回调、入口/返回模式与启停状态。成功后 ID、目标地址和 trampoline 地址保持不变，实际配置变更递增 `generation`，相同配置不递增。

实现先备份配置与 trampoline，再重建代码和入口链；失败时尝试恢复。若恢复代码或入口链再次失败，返回 `EIO` 并通过 `needs_rebuild` 保留停止状态，不能保证继续运行旧配置。调用方应检查所有返回值并保留会话处理故障。模式切换还需满足在途返回槽和同地址链的限制。

## 8. 事件时间、文本导出与合流（A3）

两套后端均在目标线程中记录硬件计数，在 tracer 消费时生成 `monotonic_ns`：

| 项目 | x86_64 | ARM64 |
| --- | --- | --- |
| 原始计数 | `LFENCE; RDTSC` | `ISB; MRS CNTVCT_EL0` |
| 换算比例 | 附加时约 5 ms 间隔的两组 TSC/时钟样本 | `CNTFRQ_EL0` 提供计数频率 |
| 时钟锚点 | `CLOCK_MONOTONIC` 采样 | `CLOCK_MONOTONIC` 采样 |
| 线程标识 | 可用时读取 FS/TLS 基址 | 读取 `TPIDR_EL0` |

`monotonic_ns` 是事件原始计数映射到单调时钟的估计值，不是热路径直接调用时钟系统接口。入口事件在可选 A4 回调之后生成。`tid` 保存 TLS 标识，tracer 根据线程记录补全 `kernel_tid`；无法映射时为 0。CPU 编号仍由格式化调用方填写，事件未采集真实 CPU 编号。

`ludp_event_format_perf()` 提供 perf-script 风格文本，入口与返回均导出 `call_id`。合流工具用整数纳秒解析和排序支持的文本记录，保留来源、TID、CPU 与原始字段；不将文本转换为 `perf.data`。

`event_merge_demo.py` 使用独立 tracefs instance 的 `mono` 时钟，与固定单 CPU 的用户态采集器协调同一批 getpid 调用。它核验两路数量、TID、CPU、唯一入口/返回配对、来源内时间单调性、采集窗口及内核事件相对入口/返回的时间偏差，结束时销毁实例。默认容差为 100,000 ns，报告同时保留实测最大偏差和内核文本时间精度；离线解析检查与真实采集分别报告，新版原生双架构结论需 CI。

单次校准没有长期漂移误差界，环的领取顺序也不保证多线程时间戳严格递增。当前真实验证限于同机同次启动、固定单 CPU 的短会话；跨 CPU、长会话及其他 perf/kprobe 采集器需独立验证。排序不构成时间精度范围内跨来源先后关系的因果证明。

## 9. 已采用的优化与测量口径

| 设计 | 影响范围 | 对应验证 |
| --- | --- | --- |
| 用户态 `JMP`/`B` 与原地汇编采集 | 减少每次事件的 trap 上下文切换 | 百万次 `getpid` 入口/入口+返回基准 |
| 预分配事件与返回记录 | 命中时不执行堆分配 | 容量、溢出和槽位复用测试 |
| ready 数组与消费水位分离 | 避免生产者顺序提交等待，便于批量读取 | 多线程、信号重入和缓冲满载测试 |
| 大块跨进程 I/O | 降低 tracer 安装/读取开销 | `LUDP_BULK_IO` 对照及 `auto_tune.py` |
| 代码槽复用与会话映射登记 | 控制重复安装后的资源增长 | 257 次复用和 `/proc/<pid>/maps` 清理检查 |
| 有截止时间的短轮询与退避 | 降低控制阶段等待停止的额外延迟 | 多线程、信号及完整清理基准 |
| 可选透明大页建议 | 降低大事件环触页和最终回收成本 | 记录策略与连续完整清理时间；普通页路径继续适用 |

批量内存访问优化位于控制侧，读取可使用 `process_vm_readv`；`process_vm_writev` 优先写路径仅用于 x86_64，ARM64 写入保留内核指令缓存同步路径。它不改变目标汇编热路径。是否达到 `< 1000 ns/次`、插入及清理 `< 10 ms` 必须以对应提交和机器的原始报告为准。当前清理门禁采用连续 `cleanup_ms`：从 remove 开始至恢复字节校验及 detach 完成，包含最终会话映射释放；同时保留 attach、remove、detach 分项。旧版 `3ffd736` 未采用该完整清理门禁。当前基准不能代替所有回调、过滤、16 探针并发或满缓冲场景的性能测试。

ABI 约定参考 [Arm 官方 AAPCS64](https://github.com/ARM-software/abi-aa/blob/main/aapcs64/aapcs64.rst)。本项目只实现本文明确列出的常规 AAPCS64 场景，完整 ABI 中的可伸缩向量等扩展不因此自动获得支持。
